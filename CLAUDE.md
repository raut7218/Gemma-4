# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local, stdlib-only (plus `pyyaml`) re-implementation of the `swegemma` evaluation loop for the Kaggle **Gemma 4 Developer Agent** competition. Three parts:

- `submission/`: the ADK agent bundle that gets zipped and submitted to Kaggle (`agent.yaml`, `prompts/system.md`, `eval_config.yaml`, `configs/sampling.yaml`). Most competition work is tuning these files.
- `harness/`: a local stand-in for the official grader, used to measure a submission before uploading it. It loads the agent tree, budgets and sampling config straight from `submission/` (or whatever `--submission` points to).
- `colab_eval/`: runs a bundle through the real swegemma 0.2.11 (not `harness/`) without Docker, against the competition checkpoint on a Colab G4, then `analyze.py` reports where tasks are lost and `timing.py` projects the 12 h Kaggle job. It also holds the LoRA pipeline (`lora/`: request logs with vLLM token ids -> `build_sft.py` -> `train_lora.py` -> `adapter.py check`). Every deviation from the Kaggle scorer is in `colab_eval/README.md`. `gpu_run.sh check` runs a bundle on 10 tasks as Kaggle would (model check, gold run of the same tasks, the bundle's own cap on the modelled L4 clock, every request logged) and `analysis/health.md` lists blank thinking, malformed tool calls, nudges and harness errors; the v11 procedure is `colab_eval/RUNBOOK_v11.md`, the v10 plan (LoRA, decision gates) `colab_eval/RUNBOOK_v10.md`.
- `bundles/`: alternative bundles, run with `--submission bundles/<name>`. `bundles/parallel-investigate/` is a SequentialAgent → ParallelAgent design; its README lists what still has to be verified against the official scorer. `bundles/v9-31b/` is v9's prompt and skills on the 31B (arm A). `bundles/v10/` is v10 as submitted (skills, 35 calls, 4.5 min; 0.12 on the LB). `submission/` is v11: the 31B with the six core tools and no skills, 8 min / 28 calls (the budget with the most finished Kaggle runs), v5's workflow plus fixes for failures measured in the v8 G4 run (short `old_string`s and recovery from malformed `edit_file` calls, exact names and exports, whole-test-file verification). v11.2 (branch `v11.2`) adds prompt fixes for what v11's 10-task G4 check showed (1/10): the model counts its calls ("Call N/28"), reads the existing test of the code it changes before the repro, writes `edit_file` strings with real line breaks, stops repeating empty greps, and edits at the first `budget_warning` if it has not yet (2/10 on the same tasks). v11.3 (branch `v11.3`) drops the call counter, which the model wrote as visible text before its first thought, and forbids `git checkout`/`stash`/`reset`/`restore` (v11.2's rich_3471 reverted its own fix that way). `bundles/v12/` (one agent, a prompt about 40% shorter than v11.3's) and `bundles/v13/` (Scout → Editor: a read-only scout ends with a text report in `output_key: scout_report`, then an editor with `include_contents: none` edits from it; ADK hands the report over as "For context: [scout] said: ...") are the two candidates after v11.3. Neither has `edit_file` or `write_file` (19 of 143 `edit_file` calls arrived malformed in the v11 G4 checks, 0 of 518 `run_command` calls): edits go through a `python3` heredoc recipe in the prompt that replaces old text only when it occurs once. Budget and sampling are v11's. On the same 10 tasks v12 and v13 resolved 0 and 1 with 5 empty patches each: as the main edit path the heredoc tripled the thinking per edit, and v13's scout used 27-29 of the 28 calls in 7 of 10 tasks. `bundles/v11.4/` is v11 plus only the two free changes: that heredoc as the fallback after a malformed `edit_file`, and the git revert ban. Branch `v5-arms` goes back to v5 (LB 0.18, our best draw): `bundles/v5` (v5 as submitted), `bundles/v5.1` (LB 0.13) and `bundles/pub024` (the public 0.24 notebook's files) are arms of four full 129-task G4 runs, with a fourth arm made by `colab_eval.variants` (v5 with the public 8192/4096 output and thinking caps); `colab_eval/RUNBOOK_v5arms.md` has the cells and the ship rule, and `python -m colab_eval.compare` ranks the runs by paired wins and losses. The public LB has 58 tasks and identical files differ by up to 6 between runs, so single submissions cannot rank bundles; local runs on the 129 public tasks can. Arms that differ only in a setting are made with `python -m colab_eval.variants`, not committed.

`submission.zip` is gitignored and goes stale; rebuild it with the bundle's files at the zip root (`agent.yaml`, `eval_config.yaml`, `configs/`, `prompts/`, and `skills/` for a bundle that has them, not inside a `submission/` folder), e.g. `cd submission && zip -r ../submission.zip .`, after running `check_bundle`. Kaggle rejects an upload not named `submission.zip`.

## Commands

There is no linter or build step. `uv run python tests/check_offline.py` is the regression check to run after changing `harness/` or a bundle: unit checks of the thinking mapping, patch stripping, checker rules and the submission's settings, `bundles/v10`'s skill scripts on the toy repo (including NEW vs PRE-EXISTING failures), then the toy task end to end with `--agent gold` (must resolve), `--agent noop` (must not) and `--agent llm` against the fake server for both `submission` and `bundles/parallel-investigate`, and `colab_eval.model_check` against the fake server. `colab_checks()` covers colab_eval's pure-Python parts (timing model, task queue, adapters, build_sft, bundle variants, the check run's sample, analyze's per-call flags and health report, model_check's verdict); `tests/check_lora.py` checks the LoRA pipeline on a CPU and needs torch, transformers 5.13.1 and peft (see its docstring). It builds its own toy data, starts the fake server on :8765 itself, and needs only `pytest` in `.venv-sandbox`. The sandbox runs `/bin/bash` and `<venv>/bin`, so it needs Linux: on Windows run it in WSL, with `UV_PROJECT_ENVIRONMENT` pointing at a Linux env outside the repo so uv doesn't rebuild the Windows `.venv` (`UV_PROJECT_ENVIRONMENT=~/v7venv uv run --with pytest python tests/check_offline.py`). The commands below are the same steps by hand.

```bash
./fetch_task.sh requests_6592 requests_6589 httpx_3672   # needs kaggle CLI; creates data/ and fetches tasks.jsonl on first use
uv run python tests/check_offline.py                                 # everything below that needs no Kaggle data, in one go
uv run python -m harness.check_bundle submission bundles/parallel-investigate   # static check of official compile rules
uv run python -m harness.run --agent gold --task-ids requests_6592   # reference patch must RESOLVE (pipeline sanity)
uv run python -m harness.run --agent noop --task-ids requests_6592   # empty patch must NOT resolve
uv run python tests/fake_llm.py &                                    # scripted OpenAI-compatible server on :8765; GET /requests shows what it was sent
uv run python -m harness.run --agent llm --base-url http://127.0.0.1:8765/v1 --model fake --task-ids requests_6592

# no Kaggle data: a toy copy of requests_6592 that the fake model's scripts also solve
uv run python tests/make_toy_task.py data-toy
uv run python -m harness.run --data data-toy --agent gold --task-ids toy_6592
uv run python -m harness.run --data data-toy --agent llm --base-url http://127.0.0.1:8765/v1 --model fake \
   --submission bundles/parallel-investigate --task-ids toy_6592

# real model on any OpenAI-compatible endpoint (vLLM, OpenRouter, AI Studio...)
# the bundle's thinking_config is sent as chat_template_kwargs.enable_thinking + thinking_token_budget (vLLM fields);
# --extra-body is merged last, so it can override them for an endpoint that wants something else
LLM_API_KEY=... uv run python -m harness.run --agent llm --base-url https://.../v1 --model <gemma-4-...> --task-ids requests_6592
```

Omit `--task-ids` to run every task in `data/tasks.jsonl` that has a snapshot in `data/snapshots/`. `--base-url` defaults to `http://127.0.0.1:8000/v1` (local vLLM) and `--model` to `gemma-4-31b-it-qat-w4a16-ct`. Other flags: `--submission DIR` (evaluate an alternative bundle), `--data DIR` (default `data/`), `--results-dir`, `--venv` (default `.venv-sandbox`).

`data/`, `data-toy/`, `results/` and `.venv*/` are gitignored and absent from a fresh clone. Commands inside the sandbox run against `.venv-sandbox` (the task repos' PyPI deps), which has to be created by hand (`uv venv .venv-sandbox`, then `uv pip install --python .venv-sandbox/bin/python pytest` plus the task repos' deps). The sandbox also shells out to the host's `git` and `patch`. Only requests and httpx tasks are set up; rich and fastapi need extra deps.

Results land in `results/<run>/`: `summary.json`, `task_results.jsonl`, and per-task `patches/`, `traces/` (the full message/tool trace) and `test_outputs/`.

## Architecture

`harness/run.py` drives each task through two phases:

1. **Agent phase.** `Sandbox` (`sandbox.py`) extracts `data/snapshots/<id>.tgz` (which includes `.git`) into a temp dir, commits it and tags it `_swegemma_baseline`. `bundle.py` loads `agent.yaml` into a tree (`!include`, `sub_agents: - config_path`, `agent_class` LlmAgent / SequentialAgent / ParallelAgent). `run_agent` (`agent.py`) runs it against `/chat/completions` with the tool schemas from `tools.py`. A single LlmAgent root runs the original loop with nudges. In a tree, parallel branches run on threads; an LlmAgent's text-only reply ends it and sets `output_key` in state; `{key}`/`{key?}` in instructions read state (missing `{key}` raises, like ADK); `include_contents: none` starts its context at the last user message or other agent's reply. When a tree finishes without `submit_patch`, it's re-run with a nudge as the user message; three nudges in a row with no tool call in between end the task (`no_tool_calls`). As in swegemma, `submit_patch` doesn't end a run: the agent can keep editing and resubmit, and the run ends at its next text-only reply. Termination reasons: `submitted`, `time`, `turns`, `context_overflow` (prompt_tokens >= 32768), `no_tool_calls` (after 3 nudges), `tool_calls`, `llm_error`. Running out of tool calls does not stop the current model turn (further calls return `BudgetExhausted`), but the run ends with `tool_calls` at the first text-only reply after that, as in swegemma's `agent_runner` (checked in 0.2.10, no nudge is sent). The patch is `git add -N . && git diff _swegemma_baseline` with the sections that touch `sandbox.PROTECTED` files removed (`sandbox.strip_protected`, as swegemma >= 0.2.10 does in `submit_patch`); when the agent never called `submit_patch`, `run.py` still grades the working-tree diff, stripped the same way.
2. **Grading phase.** `verify.py` builds a *fresh* sandbox, strips protected sections from the patch again, applies it (several `git apply` fallbacks, then `patch`), resets any file matching `sandbox.PROTECTED` (tests, conftest, pyproject, etc.), applies the hidden `test_patch`, and runs pytest with JUnit output on the test files it touched.

`classify()` in `run.py` maps the outcome to RESOLVED / CONTEXT_OVERFLOW / BUDGET_EXHAUSTED / LOOP_BREAKOUT / PATCH_REJECTED / TESTS_FAILED / NO_PATCH / LLM_ERROR, plus TEST_PATCH_FAILED and NO_JUNIT passed through from `verify.py` (both point at the harness or sandbox venv, not the agent). BUDGET_EXHAUSTED (`time`, `turns`, `tool_calls`), LOOP_BREAKOUT, LLM_ERROR and NO_PATCH are only reported for an empty patch; a non-empty patch is always graded, whatever ended the run.

Details that are easy to get wrong:

- **Resolution criterion.** `tasks.jsonl` has no FAIL_TO_PASS/PASS_TO_PASS, so "required tests" are the tests that pass with the gold patch. They're computed once and cached in `data/reference/<id>.json`. Delete that file if the grading environment changes.
- **Path rewriting.** The sandbox isn't Docker. `Sandbox.rewrite` turns `/workspace` and `/tmp` in agent commands into per-sandbox dirs, and `PYTHONPATH` points at the workspace (plus `src/`) instead of an editable install.
- **Budgets** come from `submission/eval_config.yaml` → `tools.Budget`, and every agent in a tree shares them through `Ctx` (tool calls and turns are counted under a lock). A tool not in an agent's `tools` list returns `UnknownTool`. `get_status` and `submit_patch` don't count against the tool-call budget. Once 20+ calls are used and 10 or fewer remain, every tool result gets a `budget_warning` injected.
- **Tool output caps** (5000 chars of stdout, 150 lines / 10000 chars per `read_file`) are set in `tools.py`, and the user prompt built in `agent.build_prompt` repeats them. Change both together.
- **Prompt templating.** `{problem_description}` and `{hints}` come from state, like any output_key. Any other `{identifier}` in an instruction is treated as a state key, so keep braces out of prompt text. The user prompt (problem, budget, rules, instructions, a 3-level workspace tree) is built in `agent.build_prompt` with the wording of swegemma 0.2.11's `build_agent_prompt`; the `read_file` limits are listed only when some agent in the bundle has that tool.
- **Sampling and thinking.** An agent's own `generate_content_config` replaces (not merges with) the bundle's `configs/sampling.yaml`, which is only the fallback for agents without one. `agent.effective_sampling` then merges the scorer's defaults underneath (`max_output_tokens: 16384`, `thinking_budget: 4096`), and `agent.chat` maps the keys to OpenAI request fields (`max_output_tokens` → `max_tokens`; `top_k` is sent as a top-level field, a vLLM extension). `agent.thinking_body` copies `adk_submission` 0.2.13: `thinking_budget` 0 turns thinking off, any budget above 0 turns it on, and `include_thoughts` only decides whether earlier thoughts stay in the history. `include_thoughts: false` without `thinking_budget: 0` therefore runs thinking with a 4096 budget and discards its text; `check_bundle` warns about it. Thinking tokens count against `max_output_tokens`.
- **Host git config is shut out.** `sandbox.GIT_ENV` sets `GIT_CONFIG_GLOBAL=/dev/null` for the harness's own git calls and for agent commands. Settings such as `diff.mnemonicPrefix` change the `a/` `b/` prefixes that `strip_protected` and `verify.patch_files` parse.
- **`!include` resolution differs between loader and checker.** `bundle.py` falls back to the bundle root when the path isn't found next to the including file; `check_bundle.py` follows the official rule (including file's directory only). A bundle can therefore run locally and still fail the check, so run `check_bundle` after moving files.
- **Skill scripts** (`bundles/v10/skills/swe/scripts/locate.py`, `check.py`; v11 has none). In the scorer, ADK's `run_skill_script` packs the whole skill into one Python file, runs it with the container's `python3` (from `/workspace`, so a temp `.adk_exec_*.py` sits there meanwhile) and `chdir`s to a temp copy of the skill first, so scripts use the absolute `/workspace` (`SWE_WORKSPACE` overrides it; the local harness sets it). Each run costs one tool call (the executor calls `check_budget`); `load_skill` is free but costs a turn, and the prompt tells the model to skip it. `args` arrive as a list, as `--key value` pairs or after `--`, so scripts take every non-flag argv entry. Their stdout reaches the model uncapped, so they cap themselves at 1500 chars, and they must always exit 0 (a non-zero exit becomes an error without the output). `SKILL.md` frontmatter needs a kebab-case `name` equal to the directory name; only `SKILL.md` and the description enter the model's context, the script sources don't. `check.py` never stashes: it labels failures by re-running them on a `git archive` copy of `_swegemma_baseline` with `PYTHONPATH` pointing there.
- **`tests/fake_llm.py`** picks a script by matching `Your role: <ROLE>` in the system prompt (the parallel-investigate roles and v13's SCOUT and EDITOR, else a single-agent default, which edits through a `run_command` heredoc when the request offers no `edit_file`), then picks the step by counting `tool` messages. It answers with a `reasoning` field when the request enables thinking and records every request's sampling fields for `GET /requests`, which is how `check_offline.py` verifies what the loop sends. The scripts are hard-coded for `requests_6592` and `toy_6592`. Update them whenever the tool schema, the role prompts or the loop's message shape changes.

## Gaps relative to the official stack

- The local harness implements only the six core tools; the graph tools (`search_similar_code`, `get_code_neighbors`, `get_code_subgraph`) return `UnknownTool` and are dropped from an agent's schema. `submission/` doesn't use them.
- Skills are implemented only as far as `run_skill_script` (no `load_skill`, `load_skill_resource`, or ADK's skill instruction text and listing, about 800 to 1000 tokens per request in the scorer). AgentTool, LoopAgent, LlmAgent `sub_agents` (transfer) and ADK context compaction aren't implemented. Agents with `include_contents: default` in a tree see only their own history, not other agents' events. Overflow is detected only from `usage.prompt_tokens` (estimated as JSON chars / 3 when the endpoint returns no usage).
- `harness/check_bundle.py` transcribes the compile rules of `adk_submission` 0.2.13 / `swegemma` 0.2.11 (field allowlists, tool and model names, `config_path`/`!include` resolution, `thinking_budget` 0..32768, state placeholders) and warns about thinking settings that don't do what they look like. It doesn't run the real compiler; `tests/compile_official.py` does, when run with a Python that has `adk_submission` installed (its docstring has the setup). The wheelhouse is updated without notice and has changed behaviour before (0.2.13 changed what `include_thoughts: false` means), so re-read the source after an update: `kaggle datasets download metric/gemma-4-developer-agent-wheelhouse -f adk_submission-<ver>-py3-none-any.whl` fetches one small wheel, and `kaggle datasets files metric/gemma-4-developer-agent-wheelhouse` lists the current versions.
- No run with the real model has been made with this harness: there is no GPU here, and `.venv-sandbox` covers only requests and httpx tasks (14 of the 129 public ones). Real-model runs go through the official swegemma instead (`data/eval/run.sh`, Docker sandbox, a hosted gemma-4-31b-it; results in `results/full_v*` and `results/smoke_v*`). The submission's settings follow public ablations (competition discussions 746250 and 747857), not local measurements. ADK's event compaction (it starts at 14,336 prompt tokens in the scorer) is also not reproduced, so context behaviour on long runs differs.
- To validate the YAML against the real `adk_submission` package, run `kaggle datasets download metric/gemma-4-developer-agent-wheelhouse` (867 MB).
